# Goal-driven distribution

Do not start with a fixed calendar. Start with the result the author needs.

## Inputs required only at this stage

- desired outcome;
- intended audience;
- real evidence that may be published;
- channels the author already controls or is willing to use;
- time, writing, visual and maintenance constraints;
- identity and privacy boundaries.

Combine these questions when distribution is the next real task. Do not ask them during repository audit.

## Select proof by project type

- Software: runnable demo, problem solved, before and after, technical proof.
- Agent Skill: same prompt with and without the Skill, raw Eval and failure limits.
- Dataset: representative rows, schema, coverage, provenance and baseline.
- Course: learner path, sample lesson, exercise and expected evidence.
- Research: question, method, reproducibility, result and uncertainty.
- Design: visual preview, source files, customization and use case.
- Portfolio: role, decision, artifact and verifiable outcome.

## Select the smallest channel set

Use channels because the intended audience is there, not because a launch template lists them. One strong GitHub page plus one relevant community may be better than six empty announcements.

## Match metrics to the goal

- First users: successful installs, completed examples, useful feedback.
- Contributors: issues converted to contributions, repeat contributors, review activity.
- Professional identity: qualified conversations, portfolio references, interview feedback.
- Directory discovery: accepted listings, referral traffic, external citations.
- General awareness: unique visitors, clones, stars and shares, without treating stars as the only result.

Never fabricate unavailable analytics. Avoid default telemetry.
