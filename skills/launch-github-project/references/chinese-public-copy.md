# 中文公开文案

中文 README、Release、项目简介和传播文案不能把英文版本逐句翻译。两种语言共享事实、证据和边界，但应分别按照本地读者的注意力、语序和传播习惯组织。

## 为什么“都翻对了”仍然没人想看

常见失败不是错别字，而是视角和节奏仍然属于英文：

- 以“某事不代表某人能够……”起句，主语长、落点晚，像翻译稿；
- 连续堆“可理解、可试用、可验证”等抽象结果，没有具体动作；
- 为了三段式节奏硬拼“能看懂、敢信、会用”，语法成立但没人这样说话；
- 先讲方法、安全和边界，读者还没产生兴趣就开始承担认知成本；
- 中英文共用一张带字图片，让中文页永远像次要版本；
- 只做“看得懂”冷读，不检查“愿不愿继续看、愿不愿试、有没有一句能复述”。
- 为了去掉 AI 味，把具体痛点和产品结果一起删掉，最后只剩“检查、核对、复核”这类内部动作。

## 中文项目页的阅读顺序

前 200 个汉字优先完成这条路径：

1. **开场**：说清读者遇到的具体问题，例如 README 像内部说明，安装入口不好找。
2. **影响**：用有根据的结果说明为什么值得处理；没有数据就不要编时间或转化率。
3. **项目作用**：一句话说明这个项目会检查或改变什么。
4. **证据**：紧接真实失败、输入输出、截图或可复现命令。
5. **行动**：给一条最短、可复制的命令或调用语句。

顺序可以调整，但不要让实现细节、维护者原则或免责声明抢走开场。

## 有力度不等于每句都像广告

力度来自具体问题和证据，不来自夸张形容词。一个自然的短句可以强调重点，但不要让标题、图片、引言和小节都重复同一种狠话。

| 弱表达 | 更好的方向 |
| --- | --- |
| 把项目变成陌生访客能理解、试用和验证的发布 | 把安装入口、实际效果和证据放到访客找得到的位置 |
| 本地能运行不代表访客能看懂、敢信、会用 | 项目已经能运行，README 和 Release 还需要收尾 |
| 提供全面、端到端的发布能力 | 检查仓库，整理发布材料，生成并复核发布包 |
| 自动化检查保障发布质量 | 自动检查负责找问题，素材权利和公开范围仍需人工确认 |

强句之后立即给事实。不要使用“最好、领先、革命性、全自动、安全可靠”等无法核验的承诺。

重点检查以下 AI 痕迹：

- 多次使用“不是……而是……”制造对立；
- 连续出现“先……再……”“能……敢……会……”等对称三段式；
- 用“别先听我吹”“真正的问题是”假装坦率；
- 每个标题都追求押节奏或像一句可转发金句；
- 图片里再写一遍正文已经说过的品牌口号；
- 用“审计、证明、打包、核验”这类方法论标签代替普通任务名称。

不要因为检测到一个破折号、一句口语或一个三项列表就重写。判断的是成组出现的机械节奏。保留作者真实的用词习惯、具体细节和不完全对称的句子。

## 母语检查

逐段做以下检查：

- 这句话会不会由中国开发者直接说给同事听？不会就重写。
- 能否把抽象名词换成具体的人、页面、文件、动作或失败？
- 主语是否太长，真正的动词是否出现得太晚？
- 是否连续使用三个“能、可、让、通过、实现”？拆成短句。
- 一段最多 240 个汉字；开场段优先控制在两句内。
- 是否有一句读者看完可以自然复述？不需要为了这句话额外制造口号。
- 中文图片中的文字是否已本地化？若没有，改用无文字图或单独生成中文版。
- 把项目名换成另一个工具，这句话是否仍然成立？如果成立，说明卖点没有写出来。
- 去掉“检查、审计、核对、优化”以后，还剩不剩用户能拿到的具体结果？如果没有，说明写的是工作流程，不是产品价值。
- 第一次试用是否足够轻，例如先返回一份只读诊断、预览或样例，而不是先要求信任一整套流程？

Humanizer 负责去掉机械语气，不负责替项目找到卖点。中文终审必须另外回答：用户正卡在哪里，这个项目第一次会给他什么，以及为什么值得现在试一次。不要把“更像人写的”和“更想让人用”合并成同一个判断。

## 双语工作方式

1. 先固定两种语言共享的事实、证据、限制和命令。
2. 分别写英文与中文的读者路径，不做逐句对照翻译。
3. 中文版单独通过“说给同事听”和“前 200 字是否说清问题”检查。
4. 比较两页是否主张一致，而不是段落、标题和语序是否一致。
5. 让不熟悉项目的中文读者回答：项目解决什么、哪条证据最可信、下一步做什么。

自动规则只能预警少量高置信度翻译腔。最终中文语感、说服力和传播欲仍然需要人工冷读。
