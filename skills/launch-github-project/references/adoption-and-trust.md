# Adoption and trust

Use this review after repository basics are sound and before recommending promotion. High stars are a trailing and confounded signal; inspect the path that produces real use.

## Adoption path

| Stage | Required evidence | Common failure |
| --- | --- | --- |
| Discovery | Search terms, repository metadata, social preview, relevant directory or community | Internal jargon or a misleading topic attracts the wrong visitor |
| Comprehension | One concrete user outcome visible before architecture and principles | The README describes the method but not what changes for the user |
| Motivation | A recognizable pain or goal, project-specific first result and low-risk trial | The copy sounds natural but could describe any tool in the category |
| First success | Minimal install or use path ending in a visible result | Maintainer scripts, optional gates or unsupported commands interrupt onboarding |
| Proof | Reproducible artifact, caught failure, comparison or real user outcome tied to the core promise | Structural checks or a narrow pilot are presented beside a broader claim |
| Repeat use | A real recurring job, update path or durable progress artifact | A naturally one-time project invents empty recurring rituals |
| Contribution | A small reproducible failure, example, translation or extension that users can submit | Governance files exist but no concrete contribution is available |

## Review order

1. Fix trust and safety defects before optimizing copy or distribution.
2. Remove friction from the first-success path.
3. Produce evidence that exercises the core promise on real artifacts.
4. Verify repository metadata, unsigned rendering and external discovery.
5. Invite a small number of real users and record where they stop.
6. Promote the useful artifact or lesson, not the fact that a repository was created.

## Project-frequency fit

- High-frequency tools can earn retention through repeated work, saved state, integrations or updates.
- Low-frequency launch or migration tools need strong artifact value, reusable pre-release checks or referrals from successful outcomes.
- Reference collections earn bookmarks and contributions when every visit exposes immediate value.
- Identity or movement projects spread through a memorable claim and an action people can display, but this pattern does not substitute for product evidence.

Do not add a website, chat community, badge, telemetry or broad compatibility claim until it has a real user job. Do not self-install, fabricate testimonials or manufacture stars to seed proof.

## Evidence language

Report separately:

- release integrity: schemas, required files, deterministic scripts and automated gates;
- behavior evidence: complete inputs, outputs, environment, method and limitations;
- adoption evidence: non-maintainer installs, first-success completion, repeat use and user-submitted failures;
- popularity: views, referrals, stars, forks and shares.

Never convert one category into another. A passing fixture suite is not user success, and a star is not proof that the project worked.
