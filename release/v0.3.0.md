# Project Publisher v0.3.0 — One publisher for the project's whole public life

Version 0.3.0 renames the Skill from Launch GitHub Project to Project Publisher and expands its public contract from one release moment to the continuing work around a project: review, naming and positioning, publication materials, evidence-led distribution, and later updates. The integrated installer also brings the bundled Humanizer and dependency guard with it, while missing or declined companions remain visible when their stage is reached.

## Should I update?

**Update now if:**

- You want one Skill to review, position, publish and keep a project's public materials synchronized instead of stopping after the first GitHub Release.
- You need naming decisions to distinguish a durable product identity from its first demo, platform or current release stage.
- You want the bundled Humanizer, dependency preflight and optional Hook installed together, with failed, declined or unavailable companions reported rather than silently skipped.

**You can defer if:**

- You rely on the published `launch-github-project` identifier and cannot update your invocation or automation yet.
- You only need the historical v0.2.0 read-only audit and do not need the integrated installer, naming workflow or later-update support.

## What changed

- Renames the project, plugin and main Skill to Project Publisher with the `project-publisher` identifier, while leaving historical Release records under their original name.
- Adds a naming and positioning workflow that separates identity, promise, capabilities and evidence; checks natural speech, guessability, real scope, room to grow, search collision and bilingual word order; and plans technical migration before a remote rename.
- Broadens the main workflow across project review, README and release preparation, evidence-led distribution and public-material synchronization after later product changes.
- Bundles Humanizer beside the main Skill and adds an integrated installer, dependency manifest and optional `UserPromptSubmit` guard Hook.
- Requires the main Skill to recheck runtime availability and tell the user which proof or workflow is affected when a dependency failed, was declined, is disabled, untrusted or unavailable.
- Adds a sentence-purpose gate so headings, navigation, calls to action and image text must state a reader pain, visible result, proof, boundary or worthwhile next step instead of merely telling someone to try or ask.

## Install or update

```bash
# After the remote repository rename
git clone https://github.com/weike-zhang/project-publisher.git
python3 project-publisher/scripts/install.py
# Skills-only alternative without the Hook or tool preflight
npx skills add weike-zhang/project-publisher --agent codex --skill project-publisher humanizer -g -y
```

## Compatibility

- The v0.3.0 integrated installer requires Python 3.10 or newer and Git; its local candidate is verified with Python 3.12.
- The bundled Humanizer and main Skill are installed into the same Skill scope. The optional Hook still requires explicit review and trust in Codex.
- The published v0.2.0 install and first read-only audit remain documented under the previous `launch-github-project` name.
- The `project-publisher` remote URL and tag remain unavailable until the repository is renamed and v0.3.0 is published with explicit authorization. Other Agent Skills hosts remain unverified unless listed separately.

## Known limitations

- A better name and complete publication surface do not prove demand, adoption, product quality or user comprehension.
- Humanizer is a voice pass, not a substitute for positioning, factual verification or evidence.
- The dependency Hook can add context but cannot call companion Skills, grant trust or replace the main Skill's runtime checks.
- Creating or renaming repositories, pushing branches, publishing Releases, changing visibility and posting externally still require exact target-specific authorization.
