# Launch GitHub Project v0.2.0 — Cleaner first audits and visual Release proof

Version 0.2.0 makes the first audit more trustworthy and the public release easier to judge. It stops treating project-level installed Skills as target-project content, shows users what a successful read-only audit returns, and adds evidence images plus update guidance to generated Release pages.

## Should I update?

**Update now if:**

- You install Skills at project scope under `.agents/skills/`; v0.2.0 prevents those dependencies from distorting project classification and public-surface findings.
- You want the README and generated Release page to show a real before/audit/after result instead of relying on feature copy.
- You maintain multiple Release specs and want CI to validate their generated pages, semantic version order and the actual extracted ZIP.

**You can defer if:**

- You only need the v0.1.2 symlink rejection and do not use project-level Skill installation or the Release-page generator.
- You are not preparing new public materials yet and the repository-only presentation changes do not affect your current workflow.

## What changed

- Excludes nested project-level Skill installations from type inference, link checks, secret checks and public-surface scanning, removing the false project classification and self-scanner findings exposed by a real Codex activation test.
- Rebuilds the English and Chinese README around the visitor's decision path, with localized outcome-led visuals, a real before/audit/after proof image and an example of the first read-only response.
- Adds purposeful-visual guidance to the Skill so future projects use images for outcomes, observable proof or sequence instead of decoration.
- Adds a native-Chinese public-copy workflow, localized text-image requirement and high-confidence translationese warning so bilingual pages share facts without reading like mirrored translations.
- Extends the structured Release-page format with optional visual proof, alt text and captions; tag-pinned URLs keep historical Release evidence stable.
- Detects public author-profile and username-change drafts that previously escaped the generic public-surface scan, while public-copy regression tests preserve the corrected repository story.
- Validates every versioned Release page by semantic version and makes CI build, list and extract the real repository ZIP instead of trusting a nominal archive step.

## Known limitations

- The published behavior comparison remains one exploratory prompt pair, not a benchmark or adoption result.
- Automated checks cannot prove asset ownership, product quality, user demand or visitor comprehension; the cold-reader and rights reviews remain manual gates.
- The release bundler rejects symlinks and non-regular files but is not a general sandbox against malicious concurrent file replacement.
- Creating repositories, pushing branches, changing visibility, publishing Releases and posting externally still require explicit target-specific authorization.
